# Provision SDK / partictl — Phase 7: Kubernetes Controller

Phases 1-6 built the `provision/` SDK and the `partictl` CLI: a declarative
plan/apply/drift surface over NATS JetStream control-plane buckets, the
partition-source bucket, partition records, application streams, and dynamic
consumers. Phase 7 adds a **Kubernetes operator** — a controller that
reconciles a `ProvisionedPartiEnv` custom resource by driving the *same*
`provision.Plan` / `provision.Apply` paths the CLI uses. The controller adds no
provisioning logic of its own; it is a consumer of the SDK, exactly as the v1
plan's roadmap states ("the controller is a consumer of the SDK, not a
replacement").

## What Ships After Phase 7

- A **nested Go module** at `k8s/` (`module github.com/arloliu/parti/v2/k8s`,
  with a `replace` to the parent). The `controller-runtime` / `k8s.io`
  dependency tree lives entirely in this module's `go.mod` — the root
  `github.com/arloliu/parti/v2` module gains **zero** new dependencies.
- A **`ProvisionedPartiEnv` CRD** (`apiVersion: parti.io/v1alpha1`): a
  structured `Spec` that mirrors the bucket-and-stream subset of
  `provision.Config` plus a `nats` connection block, and a `Status` carrying
  standard conditions and last-plan / last-apply summaries.
- A **controller-runtime Reconciler** that maps a CR to a `provision.Config`,
  connects to NATS, runs `Validate` → `ValidateLive` → `Plan` → `Apply`, and
  records the outcome on the CR's status subresource.
- An **operator binary** (`k8s/cmd/manager`) with manager wiring, leader
  election, and health/metrics endpoints.
- **Generated artifacts**, committed: `zz_generated.deepcopy.go` and the CRD
  YAML manifest (both produced by `controller-gen`).
- **Deploy manifests** under `k8s/config/`: the CRD, RBAC, an operator
  Deployment + ServiceAccount, and a sample CR.
- **`docs/KUBERNETES.md`** — an operator guide, plus a cross-link from
  `docs/PROVISION.md` and a `CHANGELOG.md` entry.
- Root `Makefile` targets `lint-k8s` / `test-k8s` / `generate-k8s` so the
  nested module is linted, tested, and regenerated by an explicit command.

## Background: The SDK-as-a-Library Surface

The operator is a thin adapter. Everything it needs already exists:

- **Input** — `provision.Config` (`provision/config.go`) and its nested
  structs `ControlPlaneConfig`, `PartitionSourceConfig`, `StreamCfg`. The
  config `apiVersion` constant is `provision.APIVersionV1` (`"parti.io/v1"`).
  The reconcile policy is `provision.ReconcilePolicy` with constants
  `PolicyWarn` / `PolicyAdopt` / `PolicySafeUpdate` / `PolicyForce`.
- **Processing** — `provision.Apply(ctx, js, cfg) (Report, error)` is the
  canonical mutation entrypoint; it internally runs `Validate`,
  `ValidateLive`, and `Plan` before executing. `provision.Plan(ctx, js, cfg)
  (PlanResult, error)` is the read-only planner; it is what surfaces
  `Drift`. `provision.Validate(cfg) error` is pure static validation.
- **Output** — `provision.PlanResult` (`Actions`, `Drift []DriftFinding`) and
  `provision.Report` (`Executed`, `Skipped`, `Errors`, `Aborted`). Drift
  severities: `informational` / `drift-mutable` / `drift-immutable` /
  `adopted`. The output envelope `apiVersion` is `parti.io/provision/v1`.
- **NATS** — `provision` functions take a `jetstream.JetStream`; they are
  connection-agnostic. The operator obtains its own connection (the
  `cmd/partictl/natsconn.go` logic is unexported and file-path oriented; the
  operator needs an equivalent that reads credentials from a Kubernetes
  Secret).

The controller's job is the glue: CR → `provision.Config` → `js` → `Apply` →
status.

### Why a nested module

`sigs.k8s.io/controller-runtime` transitively pulls `k8s.io/api`,
`k8s.io/apimachinery`, `k8s.io/client-go`, `k8s.io/klog`, and dozens more.
`github.com/arloliu/parti/v2` is a NATS partitioning library; every consumer
of it would inherit that tree if the controller lived in the main module. The
repo already isolates a heavy, optional component this way —
`test/iops-investigation/go.mod` is a nested module with a
`replace github.com/arloliu/parti/v2 => ../..` directive, and the root
`Makefile`'s `TEST_DIRS` explicitly excludes it. Phase 7 follows that
precedent.

### Why the controller reconciles only buckets and streams

`provision.Apply` reconciles control-plane KV buckets, the partition-source
bucket, and application streams — *durable infrastructure*. Two other
`provision` surfaces are deliberately **excluded** from the controller's
reconcile loop (see Non-Goals): partition-record contents and dynamic-consumer
precreation. Both are managed at runtime by the Parti library itself; a
controller that re-applied a declared partition table or re-precreated
consumers on every resync would fight the runtime's own ownership of those
resources. They remain `partictl`-operator-driven one-shot operations.

## Invariants Inherited from Phases 1-6

The controller is a pure SDK consumer, so every Phase 1-6 invariant holds
unchanged — the controller must not weaken any of them:

- **No duplicated provisioning logic.** The controller calls `provision.*`
  exclusively. It never re-implements planning, drift classification,
  byte-equivalent config building, or the apply sequence.
- **Ownership marker** (`parti.io/managed`, `parti.io/component`,
  `parti.io/instance`) stays in resource `Metadata`, informational only —
  the controller does not read or stamp it directly; `provision` does.
- **JSON / output envelope** stays `parti.io/provision/v1`; **input config**
  stays `parti.io/v1`. The CRD's `parti.io/v1alpha1` is a *separate*
  Kubernetes API group/version and does not collide with either.
- **Deterministic ordering** of `Plan` actions and drift — the controller
  surfaces counts, so ordering does not affect status, but the controller
  must not re-sort or re-interpret SDK output.
- **`provision` cancellation semantics** — `Apply` honors `ctx`
  cancellation (`Report.Aborted`); the controller passes the reconcile
  `ctx` straight through. A cancelled mid-apply is classified
  `ClassApplyAborted` and treated as a transient interruption, **not** a
  resource failure — it is never recorded as `ApplyError` (see W4).
- The controller introduces **no new `provision` exported symbols** unless a
  genuinely shared helper is required (see W3 — none is currently expected;
  the NATS-connection glue lives in the `k8s/` module).

## Non-Goals (Phase 7)

- **Partition-record reconciliation.** The CRD `Spec` omits the partition
  table; the controller never calls `PlanPartitions` / `ApplyPartitions`.
  Reason: the runtime owns the partition table; continuous reconcile would
  fight it. Partition records stay a `partictl partitions` operation.
- **Dynamic-consumer precreation or alignment.** The CRD `Spec` omits
  `dynamicConsumers` entirely; the controller never calls `PlanConsumers` /
  `ApplyConsumers`. Reason: Phase 5's runtime-owns model — consumers carry no
  marker and the runtime overwrites them via `CreateOrUpdateConsumer`; a
  controller re-precreating them would oscillate.
- **Deprovisioning on CR deletion.** No finalizer. Deleting a
  `ProvisionedPartiEnv` stops reconciliation; it does **not** delete any NATS
  resource. `provision` has no delete-all path, and silently destroying
  buckets on a `kubectl delete` would be a dangerous surprise. Documented
  explicitly in `docs/KUBERNETES.md`.
- **`envtest`-based integration tests.** `envtest` requires downloaded
  `kube-apiserver` / `etcd` binaries. Phase 7 tests use the in-memory
  controller-runtime **fake client** plus an **embedded NATS server**
  (`partitest.StartEmbeddedNATS`) — fully self-contained, no external
  binaries.
- **Admission / mutating webhooks.** Validation is CRD OpenAPI schema only
  (kubebuilder validation markers). No webhook server.
- **Helm chart, Kustomize overlays, or OLM packaging.** Phase 7 ships plain
  YAML manifests under `k8s/config/`. Packaging is a cross-cutting follow-up.
- **The operator does not manage NATS itself.** It connects to an existing,
  externally-managed NATS cluster.
- **Templating / multi-environment overlays** of the CR — that is the
  separate cross-cutting "templating story" follow-up.

## Design

The work is split into eight items, W0-W7. W4 (the Reconciler) is the sharp
one — controller-runtime requeue/condition/conflict semantics are the only
genuinely new ground. W0-W3 are scaffolding and mechanical mapping; W5-W7 are
wiring, manifests, and docs.

All paths below are relative to the worktree root unless noted; everything
under `k8s/` is the nested module.

### W1 — CRD API types

`k8s/api/v1alpha1/` — the Go types that define the CRD.

- **`groupversion_info.go`** — `GroupVersion{Group: "parti.io", Version:
  "v1alpha1"}`, the `SchemeBuilder`, and `AddToScheme`. Standard
  kubebuilder-style file.
- **`provisionedpartienv_types.go`** — the resource:
  - `ProvisionedPartiEnv` (`metav1.TypeMeta` + `metav1.ObjectMeta` + `Spec` +
    `Status`) and `ProvisionedPartiEnvList`. Markers:
    `+kubebuilder:object:root=true`, `+kubebuilder:subresource:status`,
    `+kubebuilder:resource:shortName=ppe`, and `+kubebuilder:printcolumn`
    entries for the `Ready` condition, the policy, and age.
  - **`ProvisionedPartiEnvSpec`** — the structured mirror:
    - `NATS NATSConnection` — **required**. `Server string` (required), and
      `CredentialsSecret *NATSAuthSecret` — a Secret reference with the
      secret `Name` plus optional `CredentialsKey` / `TokenKey` / `NKeyKey`
      naming which data keys hold a NATS `.creds` file, a token, or an nkey
      seed. Exactly one auth key may be set; none = anonymous. (The Secret is
      in the CR's namespace.)
    - `Instance string` — optional; maps to `Config.Instance`.
    - `Policy string` — optional;
      `+kubebuilder:validation:Enum=warn;adopt;safe-update;force`; maps to
      `Config.Policy`. Empty = `warn` (the SDK default).
    - `ControlPlane *ControlPlaneSpec` — optional; mirror of
      `provision.ControlPlaneConfig`. The five bucket-name strings, the four
      TTL fields as **`metav1.Duration`** (`WorkerIDTTL`, `ElectionTimeout`,
      `HeartbeatTTL`, `AssignmentTTL`, `HandoffTTL`),
      `EnableTwoPhaseHandoff bool`, `Replicas int`, `AllowDeleteRecreate
      bool`.
    - `PartitionSource *PartitionSourceSpec` — optional; mirror of
      `provision.PartitionSourceConfig` **minus `Partitions`**. `Bucket`,
      `Key`, `Replicas`, `Storage`
      (`+kubebuilder:validation:Enum=file;memory`), `History`,
      `MaxValueSize`, `TTL metav1.Duration`, `AllowDeleteRecreate`.
    - `Streams []StreamSpec` — optional; each mirrors `provision.StreamCfg`.
      `Name`, `Subjects []string`, `Retention`
      (`+kubebuilder:validation:Enum=limits;workqueue;interest`), `Storage`
      (`Enum=file;memory`), `Discard` (`Enum=old;new`), `Replicas`, `MaxAge
      metav1.Duration`, `MaxBytes`, `MaxMsgs`, `Description`,
      `AllowDeleteRecreate`.
    - **Omitted by design:** `Config.DynamicConsumers` and
      `PartitionSourceConfig.Partitions` (Non-Goals). The mapping (W2) sets
      both to their zero value; the completeness test's allowlist names them.
  - **Numeric field types and validation bounds.** Kubernetes API convention
    uses `int32` / `int64`, never `uint8` — and the CRD OpenAPI schema must
    bound any field whose SDK type is narrower than the CRD type, so the API
    server rejects an out-of-range value *before* the mapper's conversion can
    silently wrap it. The completeness test (W2) proves fields are *mapped*,
    not that they are *range-safe* — the bounds below are the range-safety
    contract:
    - `PartitionSourceSpec.History` — SDK type is `uint8`. CRD field is
      `int32` with `+kubebuilder:validation:Minimum=0` and
      `+kubebuilder:validation:Maximum=255`. W2's mapper converts `int32` →
      `uint8`; the OpenAPI bound guarantees the value is in range, and the
      mapper additionally guards the conversion (a value outside 0-255 — only
      reachable if the CRD schema is bypassed — is clamped-and-flagged or
      returns a mapping error; see W2).
    - `PartitionSourceSpec.MaxValueSize` — SDK type `int32`. CRD field
      `int32` with `+kubebuilder:validation:Minimum=0`.
    - `Replicas` (control-plane, partition-source, stream) — SDK type `int`.
      CRD field `int32` with `+kubebuilder:validation:Minimum=0`.
    - `StreamSpec.MaxBytes` / `MaxMsgs` — SDK type `int64`. CRD field `int64`
      with `+kubebuilder:validation:Minimum=0` (0 = unlimited).
    - Duration fields (`metav1.Duration`) — OpenAPI represents these as
      strings; a numeric `Minimum` marker does not apply. Negative durations
      are rejected by `provision.Validate` downstream, so no CRD-level bound
      is added; the mapping is a pure pass-through and W4's `InvalidSpec`
      branch surfaces a bad TTL.
  - **`ProvisionedPartiEnvStatus`** — observation only:
    - `ObservedGeneration int64` — the `.metadata.generation` the last
      reconcile acted on.
    - `Conditions []metav1.Condition` — a **single** condition type,
      `Ready`, carrying the reconcile outcome via its `Status` + `Reason`.
      `Ready=True` reason `Reconciled` (the last reconcile applied cleanly).
      `Ready=False` with reason ∈ `InvalidSpec` / `SecretMissing` /
      `NATSUnreachable` / `ApplyError`. A single condition (no separate
      `Reconciling` / `Degraded`) is deliberate: a transient in-flight
      `Reconciling=True` that an early-return branch fails to clear is a real
      stuck-status bug, and `Degraded` would merely be the inverse of
      `Ready`. The `Reason` field carries all the granularity an observer
      needs. There is deliberately **no `Aborted` reason**: a cancelled
      reconcile (`ClassApplyAborted`, see W3/W4) runs on a dead `ctx` and
      persists *no* status write at all — the next reconcile on a fresh
      `ctx` records the real outcome, so an `Aborted` reason could never be
      observed.
    - `LastReconcileTime *metav1.Time`.
    - `LastPlan *PlanSummary` — `ActionCount int`, and a drift count per
      severity (`DriftInformational`, `DriftMutable`, `DriftImmutable`,
      `DriftAdopted` — all `int`).
    - `LastApply *ApplySummary` — `ExecutedCount`, `SkippedCount`,
      `ErrorCount` (`int`), `Aborted bool`, and `Errors []string` — the
      `ResourceError` messages, **capped** (first N, e.g. 10) so the status
      object stays small.
    Status carries **counts and short messages, never raw `PlanResult` /
    `Report` payloads** — CRD status objects have size limits and every
    write is an etcd round-trip.
- **`zz_generated.deepcopy.go`** — generated by `controller-gen object`. The
  exact invocation, pinned, is specified in W6 and wired as the
  `generate-k8s` Make target; the generated file is committed.

W1 deliverable: `cd k8s && go build ./api/...` succeeds; the deepcopy file is
present and committed.

### W2 — Spec → `provision.Config` mapping

`k8s/internal/controller/mapping.go` (or a `mapping` sub-package).

- **`func toProvisionConfig(spec v1alpha1.ProvisionedPartiEnvSpec)
  (provision.Config, error)`** — a near-pure function. Sets `APIVersion =
  provision.APIVersionV1`, copies `Instance`, converts `Policy` (empty →
  leave empty; the SDK defaults it), and maps each nested struct.
  `metav1.Duration` → `time.Duration` is `d.Duration`. Pointer-nested specs
  (`ControlPlane`, `PartitionSource`) map to pointer-nested configs; a nil
  spec pointer → a nil config pointer.
  - The function does **no semantic validation** — `provision.Validate` owns
    that. It returns a non-nil error for exactly ONE class of problem: a
    **narrowing numeric conversion that would silently wrap**. The only such
    field is `PartitionSourceSpec.History` (`int32` in the CRD →`uint8` in
    the SDK). The CRD OpenAPI `Maximum=255` bound makes an out-of-range value
    unreachable through a real API server, but the controller-runtime **fake
    client used in tests does not enforce OpenAPI**, so the mapper guards the
    conversion: `History` outside 0-255 → return a descriptive error rather
    than `uint8(spec.History)` wrapping. W4 maps a `toProvisionConfig` error
    to the `Ready=False` reason `InvalidSpec` (no requeue).
  - Every other field maps without the possibility of error; the error
    return exists solely so the `History` narrowing cannot wrap silently.
- **Schema-drift discipline (the load-bearing test).** A structured mirror
  silently rots when a future phase adds a field to `provision.Config` or a
  nested struct: the mapping still compiles, and the new field is simply
  never set. W2 ships a guard test, `TestMappingCompleteness`:
  1. Construct a `ProvisionedPartiEnvSpec` with **every** field set to a
     distinctive non-zero value (every string non-empty, every int/duration
     non-zero, every bool true, every slice non-empty, every pointer
     non-nil).
  2. Map it with `toProvisionConfig`.
  3. **Reflection-walk the resulting `provision.Config` recursively** and
     assert that every exported field is non-zero — *except* an explicit
     allowlist: `Config.DynamicConsumers` and
     `PartitionSourceConfig.Partitions` (the documented Non-Goal omissions).
  A new `provision.Config` field that the mirror does not carry stays zero
  after the map and **fails the test**, forcing a conscious decision: add it
  to the mirror, or add it to the allowlist with a reason. The allowlist is
  the discipline — it is small, explicit, and reviewed.
- Per-field unit tests cover the `metav1.Duration` conversion and the
  nil-pointer cases.

### W3 — NATS connection + the provisioning core

`k8s/internal/controller/nats.go` and `provisioner.go`.

- **`func connectNATS(ctx context.Context, conn v1alpha1.NATSConnection,
  secret *corev1.Secret) (*natsConn, error)`** — builds `nats.Option`s from
  `conn.Server` plus, when `conn.CredentialsSecret` is set, the auth material
  read out of `secret.Data` by the named key. The exact `nats.go v1.50.0`
  APIs (the helper version `nats.UserCredentials` / `nats.NkeyOptionFromSeed`
  used by `cmd/partictl/natsconn.go` are **file-path** oriented and do NOT
  fit Secret bytes — all three modes below are in-memory):
  - **`.creds` bytes** (`CredentialsKey`) → `nats.UserCredentialBytes(
    secret.Data[key])` — in-memory, no temp file.
  - **token** (`TokenKey`) → `nats.Token(string(secret.Data[key]))`.
  - **nkey seed** (`NKeyKey`) → fully in-memory via `nats.Nkey(pubKey,
    sigCB)`. `nats.NkeyOptionFromSeed` takes a file **path** and re-opens
    that file on *every* nonce signature — including reconnect-time
    signatures, long after the initial `nats.Connect` returns — so a temp
    file deleted post-connect silently breaks reconnection after a NATS
    server restart. Instead, parse the seed bytes once with
    `nkeys.FromSeed(secret.Data[key])` (package `github.com/nats-io/nkeys`,
    already a transitive dependency of `nats.go`), derive `pubKey` from
    `kp.PublicKey()`, verify it with `nkeys.IsValidPublicUserKey(pubKey)`
    (the file-based `NkeyOptionFromSeed` performs this `U`-prefix check
    internally — `nats.Nkey` does not, so the in-memory path must replicate
    it; an account / operator / server seed fails here with a clear
    pre-connect message instead of an opaque server-side auth rejection),
    and pass a signature callback
    `func(nonce []byte) ([]byte, error) { return kp.Sign(nonce) }` to
    `nats.Nkey`. The `nkeys.KeyPair` is held by the returned `natsConn`
    wrapper so it stays live for the connection's whole lifetime (every
    reconnect signature included); `natsConn.close()` calls `kp.Wipe()`. No
    temp file is ever created. A malformed seed fails fast at
    `nkeys.FromSeed`, and a non-user seed at `IsValidPublicUserKey` — both
    before any connect attempt, surfaced as a plain error (neither sentinel
    → W4 routes to `NATSUnreachable`).
  - **Auth-key rules and error classification.** `connectNATS` returns a
    *classified* error so W4 can pick the correct `Ready=False` reason
    without re-inspecting the raw error string:
    - At most one of `CredentialsKey` / `TokenKey` / `NKeyKey` may be set.
      More than one → an error wrapping the sentinel `errAuthSpecInvalid`
      (W4 → `InvalidSpec`). A pure pre-connect check.
    - A named auth key absent from `secret.Data` → an error wrapping the
      sentinel `errSecretKeyMissing` (W4 → `SecretMissing`). Also a
      pre-connect check.
    - Any other failure — a malformed `.creds` / nkey seed rejected while
      building the option, or `nats.Connect` itself failing (network
      unreachable, auth rejected by the server) → a plain error wrapping
      *neither* sentinel (W4 → `NATSUnreachable`).
    - No auth key set → anonymous connection.
    W4 distinguishes the three with `errors.Is(err, errAuthSpecInvalid)` /
    `errors.Is(err, errSecretKeyMissing)`, defaulting to `NATSUnreachable`.
    The two sentinels are unexported package-level `errors.New` values in
    the controller's `nats.go` file (not the NATS client library).
  Returns a wrapper holding `*nats.Conn` + `jetstream.JetStream` — and, on
  the nkey path, the `nkeys.KeyPair` — with a `close()` that closes the
  connection and (nkey path) wipes the key pair. The connection carries no
  async subscriptions (the operator issues only request/reply JetStream API
  calls), so `nats.Conn.Close()` is sufficient — there is nothing to drain. `nats.Connect` does not
  take a `ctx`; check `ctx.Err()` immediately after, mirroring
  `cmd/partictl/natsconn.go:71`. Connection is **per-reconcile** — connect
  at the start, `defer close()` — which suits the reconcile cadence and
  needs no pooling.
- **`func runProvision(ctx, js, cfg) (provisionOutcome, error)`** — the SDK
  driver. Steps:
  1. `provision.Validate(cfg)` — static. An error here → return immediately
     with classification `ClassValidation`.
  2. `provision.Plan(ctx, js, cfg)` — read-only; `PlanResult.Drift` is the
     source of the status drift counts. `provision.Plan` returns `ctx.Err()`
     from its entry guard and after each sub-planner
     (`provision/plan.go:34`, `provision/plan.go:54`, `provision/plan.go:63`,
     `provision/plan.go:72`), so a `Plan` error that wraps `context.Canceled`
     / `context.DeadlineExceeded` → `ClassApplyAborted`; any other `Plan`
     error → `ClassTransientNATS` (with a statically-valid config, a
     non-cancellation `Plan` failure is a NATS/IO problem).
  3. `provision.Apply(ctx, js, cfg)` — the mutation. `Apply` re-validates and
     re-plans internally; the extra `Plan` in step 2 buys the drift summary
     and is cheap (read-only).
  - **Cancellation is classified first.** Before inspecting `Report` shape,
    `runProvision` checks the returned error: if it wraps `context.Canceled`
    or `context.DeadlineExceeded`, the class is `ClassApplyAborted` —
    regardless of which step produced it or whether `Report.Aborted` is set.
    `provision.Apply` surfaces a cancelled `ctx` in two distinct shapes: a
    pre-action cancel inside its internal `ValidateLive` / `Plan` returns a
    **zero `Report{}`** plus `ctx.Err()` (`provision/apply.go:62`,
    `provision/apply.go:68`), while a cancel inside the action loop returns a
    partial `Report{Aborted: true}` plus `ctx.Err()`
    (`provision/apply.go:115`). Classifying on the *error* (not on
    `Report.Aborted`) collapses both — and the step-2 `Plan` cancel — into
    the single `ClassApplyAborted` outcome.
  - **`provisionOutcome`** carries `Plan provision.PlanResult`, `Report
    provision.Report`, and `Class provisionClass`. It **always preserves the
    partial `Report`** that `Apply` returns — `Apply` returns a populated
    `Report` *together with* a non-nil error for both a mid-apply
    cancellation and a resource-level failure, and that `Report` is the
    status payload (`Executed` / `Errors`). The outcome is never discarded in
    an error branch.
  - **`provisionClass`** is an explicit enum, set once by `runProvision`:
    - `ClassApplyAborted` — *checked first*: any step returned an error
      wrapping `context.Canceled` / `context.DeadlineExceeded` (the reconcile
      `ctx` was cancelled — during the step-2 `Plan`, inside `Apply`'s
      pre-action `ValidateLive` / `Plan`, or inside `Apply`'s action loop).
      The W4 branch for this class skips the status write entirely (dead
      `ctx`).
    - `ClassOK` — `Apply` returned a nil error.
    - `ClassValidation` — step 1 failed (static-invalid config).
    - `ClassTransientNATS` — step 2 `Plan` failed with a **non-cancellation**
      error, or `Apply` returned a non-cancellation error with an **empty**
      `Report` (a connect/IO failure before any mutation).
    - `ClassApplyResourceError` — `Apply` returned a non-cancellation error
      **with** a non-empty `Report.Errors` (some resource(s) rejected).
  - `runProvision` does the classification once; W4 branches purely on
    `outcome.Class`, never re-inspecting the raw error. This is what
    prevents an apply-resource failure from being mis-routed as
    `NATSUnreachable`, and a cancelled reconcile from being mis-routed as a
    transient NATS fault that `finish` would then try to record on a dead
    `ctx`.
- W3 is testable on its own with an **embedded NATS server**
  (`partitest.StartEmbeddedNATS`) — no Kubernetes involved. A W3 test forces
  `Apply` to return `Report.Errors` + a non-nil error and asserts
  `runProvision` preserves the `Report` and sets `ClassApplyResourceError`.

### W4 — The Reconciler

`k8s/internal/controller/provisionedpartienv_controller.go` — the
`ProvisionedPartiEnvReconciler`, implementing `reconcile.Reconciler`. This is
the sharp work item.

**The terminal-status invariant.** Every reconcile path *after the CR fetch*
funnels through one helper, `finish` — no branch returns without either
persisting a terminal status or, when the reconcile `ctx` is already dead,
returning the cancellation. This closes the plan-review gap where an early
failure (missing Secret, NATS down) could return for backoff without ever
recording `Ready=False`.

`finish(ctx, cr, reason, plan, apply, result, retErr) (ctrl.Result, error)` —
the single terminal status write:
- **Dead-`ctx` bypass (first action).** `finish` checks `ctx.Err()` before
  anything else. If non-nil, the reconcile was cancelled (manager shutdown)
  and a `client.Status().Update` on a dead `ctx` would itself fail — `finish`
  skips the write and returns `(ctrl.Result{}, ctx.Err())`, overriding the
  caller's intended `(result, retErr)`. This is one cancellation policy
  applied at a single chokepoint: *every* pre-provision cancellation window —
  a `ctx` cancelled before or during the step-3 Secret read or the step-4
  `connectNATS`, surfacing as an error that wraps `context.Canceled` /
  `context.DeadlineExceeded` and routing to `finish` like any other failure —
  is caught here. The `ClassApplyAborted` branch (step 5) is the one path
  that returns *before* calling `finish`, because `runProvision` has already
  classified the abort; its return value is identical to what this bypass
  produces.
- **Capture before retry.** `finish` snapshots `gen := cr.Generation` and the
  computed status fields (the `Ready` condition, `LastReconcileTime = now`,
  `LastPlan` / `LastApply`) *before* entering the retry loop.
- Sets the `Ready` condition: `True` reason `Reconciled` when `reason ==
  Reconciled`, else `False` with the given failure reason.
- Sets `LastPlan` / `LastApply` from the `plan` / `apply` arguments when
  non-nil; a failure branch with no SDK outcome passes nil and leaves the
  prior summaries untouched.
- **Status write with conflict retry.** Inside `retry.RetryOnConflict(
  retry.DefaultRetry, …)`: re-fetch the CR, re-apply the *captured* status
  fields onto the fresh object — including `ObservedGeneration = gen`, the
  generation this reconcile actually acted on, **never** the re-fetched
  object's (possibly newer) `.metadata.generation` — and call
  `client.Status().Update`. A 409 on the status subresource is routine and
  retried; using the captured `gen` ensures an outcome computed for
  generation N is never stamped as observed for generation N+1 when a spec
  edit lands mid-retry.
- **Status-write failure precedence.** If `RetryOnConflict` returns an error —
  conflict retries exhausted, or a non-conflict API error (RBAC denial,
  apiserver outage, `ctx` cancelled mid-write) — `finish` returns
  `(ctrl.Result{}, thatErr)`, overriding the caller's intended
  `(result, retErr)`. A failed terminal-status write must surface as a
  non-nil `Reconcile` error so controller-runtime requeues; it must never be
  masked by a nil-error caller branch (`InvalidSpec` / `ClassValidation`
  return nil otherwise) that would drop the CR with its status never
  persisted.
- On a successful write, returns `(result, retErr)` — the caller's intended
  requeue regime.

**`Reconcile(ctx, req) (ctrl.Result, error)`** — the sequence:

1. **Fetch** the `ProvisionedPartiEnv`. `apierrors.IsNotFound` → return
   `ctrl.Result{}, nil` (deleted; no finalizer; nothing to persist). Any
   other fetch error → return it (controller-runtime backoff; no status to
   write — the object could not be read).
2. **Map** `Spec` → `provision.Config` via `toProvisionConfig` (W2). A
   mapping error (the `History` narrowing guard) → `finish(reason:
   InvalidSpec, result: {}, retErr: nil)` — no requeue.
3. **Read the NATS auth Secret** when `Spec.NATS.CredentialsSecret` is set,
   from the CR's namespace. Not found / unreadable → `finish(reason:
   SecretMissing, result: {}, retErr: secretErr)` — status persisted, then
   the error is returned so controller-runtime applies exponential backoff.
4. **Connect to NATS** (W3 `connectNATS`); on success `defer close()`. A
   failure carries a *classified* error (W3) — W4 routes it without
   re-parsing: `errors.Is(connErr, errAuthSpecInvalid)` → `finish(reason:
   InvalidSpec, result: {}, retErr: nil)` — no requeue, a spec mistake is
   not a transient fault; `errors.Is(connErr, errSecretKeyMissing)` →
   `finish(reason: SecretMissing, result: {}, retErr: connErr)` — backoff;
   any other error → `finish(reason: NATSUnreachable, result: {}, retErr:
   connErr)` — backoff.
5. **Run `runProvision`** (W3) and branch purely on `outcome.Class` —
   `runProvision` always returns the partial `outcome.Plan` / `outcome.Report`
   even on error, so every branch can pass them to `finish`:
   - `ClassOK` → `finish(reason: Reconciled, plan, apply, result:
     {RequeueAfter: resyncPeriod}, retErr: nil)` — periodic drift re-check.
   - `ClassValidation` → `finish(reason: InvalidSpec, plan, apply, result:
     {}, retErr: nil)` — no requeue; the CR watch delivers the next event on
     a spec edit.
   - `ClassTransientNATS` → `finish(reason: NATSUnreachable, plan, apply,
     result: {}, retErr: outcomeErr)` — backoff.
   - `ClassApplyResourceError` → `finish(reason: ApplyError, plan, apply,
     result: {RequeueAfter: resyncPeriod}, retErr: nil)` — `LastApply` carries
     the executed/error counts and the capped `Report.Errors`; this is
     "converged as far as possible", a periodic recheck, **not** a tight
     backoff crash-loop (a resource error usually needs a spec or
     environment fix).
   - `ClassApplyAborted` → the reconcile `ctx` was cancelled (manager
     shutdown) — observed during the step-2 `Plan`, inside `Apply`'s
     pre-action checks, or inside its action loop; `runProvision` collapses
     all three into this class. Return `ctrl.Result{}, ctx.Err()` directly
     **without calling `finish`**: `runProvision` has already classified the
     abort, so routing through the helper buys nothing. The result is byte-
     identical to `finish`'s own dead-`ctx` bypass — no status is persisted
     for an aborted reconcile; the next reconcile (fresh `ctx`) records the
     real outcome. Every *other* cancellation window is covered by that
     bypass inside `finish`, so this explicit early return and the `finish`
     guard are the same policy applied at the two points it can be reached.

The requeue regimes above are the complete set: success / apply-resource
error → `RequeueAfter: resyncPeriod`; transient (Secret, NATS) → return the
error for exponential backoff (no `RequeueAfter`); validation failure → no
requeue; aborted → `ctx.Err()`.
- **`SetupWithManager`** — `ctrl.NewControllerManagedBy(mgr).For(&v1alpha1.
  ProvisionedPartiEnv{}).Owns(nothing).Complete(r)`. The reconciler also
  needs RBAC to `get` Secrets; declared via `+kubebuilder:rbac` markers (W6).
- **Multiple CRs** — standard controller-runtime behavior: N
  `ProvisionedPartiEnv` resources each reconcile independently, each opening
  its own per-reconcile NATS connection. Supported and covered by a W4 test.
- **`force` policy** — the controller honors `Spec.Policy` verbatim,
  including `force`. Once the environment is converged, `force` is a no-op
  (the Phase 6 apply-time re-read short-circuits `recreate-*` when the
  immutable drift is already gone), so continuous reconcile is safe. The
  *implication* — an operator edit to an immutable field triggers a
  delete/recreate on the next reconcile — is documented prominently in
  `docs/KUBERNETES.md`. The plan's position: honor `force` (idiomatic — the
  CR is the declared desired state); do not cap the policy ladder.

**Status-write rule.** A reconcile performs **at most one** status write — the
`finish` helper — per invocation (the `ClassApplyAborted` branch, and any
other branch reaching `finish` with a dead `ctx`, performs zero). There is no
separate in-flight `Reconciling` write, which is what eliminates the
stuck-status failure mode. Every write goes through `RetryOnConflict`;
`ObservedGeneration` is set to the generation captured *before* the retry loop
(never the re-fetched object's) and the `Ready` condition carries pass/fail. A
`RetryOnConflict` failure is propagated as a non-nil `Reconcile` error so the
terminal status is eventually persisted on requeue.

  asserts the **persisted** status (re-fetch the CR after `Reconcile`), not
  just the return value: `Ready` status + condition `Reason`,
  `ObservedGeneration` set to the reconciled generation, and the requeue
  regime.
  - **Fake-client harness.** The fake client does not infer a custom CRD's
    status subresource from kubebuilder markers — it must be registered with
    `fake.NewClientBuilder().WithStatusSubresource(&v1alpha1.
    ProvisionedPartiEnv{})`. Without that registration the fake client does
    not model the apiserver's status-subresource separation: a plain
    `client.Update` would persist status changes too, and a
    `client.Status().Update` on the unregistered custom GVK returns
    `NotFound` — the reconciler's status writes would then fail spuriously
    in tests. With it registered, `Status().Update` copies only status
    fields and a plain `Update` leaves status untouched, matching the real
    apiserver. The injected-failure cases (the 409-conflict and the
    non-conflict status-write-failure tests below) use the builder's
    `WithInterceptorFuncs` hook to fail the `Status().Update` call.
  - Happy path: a `ProvisionedPartiEnv` + its Secret → `Ready=True` reason
    `Reconciled`, `LastApply` / `LastPlan` counts populated,
    `ObservedGeneration == cr.Generation`, `RequeueAfter == resyncPeriod`.
  - CR not found → `Result{}`, nil error, no panic.
  - Secret missing → persisted `Ready=False` reason `SecretMissing`, non-nil
    returned error (backoff).
  - NATS unreachable → persisted `Ready=False` reason `NATSUnreachable`,
    non-nil returned error.
  - Invalid spec (a bad bucket name, or `History` out of range) → persisted
    `Ready=False` reason `InvalidSpec`, `Result{}`, **no requeue**, nil error.
  - Apply resource error → persisted `Ready=False` reason `ApplyError`,
    `LastApply` error count + capped messages, `RequeueAfter == resyncPeriod`,
    nil returned error.
  - Aborted: a `ctx` cancelled during reconcile → `Result{}` + `ctx.Err()`,
    **no** status write attempted (the dead `ctx` would fail it). Cover
    every cancellation window so the `finish` dead-`ctx` bypass and the
    `ClassApplyAborted` early return are both exercised: cancel *before* the
    Secret read, cancel *during/after* `connectNATS`, cancel inside `Plan`,
    and cancel mid-apply. Each must persist no status and return `ctx.Err()`.
  - Status-update conflict on a **failure** path (not only the happy path): a
    409 on the `finish` write → `RetryOnConflict` recovers; the final
    persisted status is the intended failure status.
  - Status-write failure precedence: a **non-conflict** error on the
    `finish` write (e.g. an injected forbidden/`apierrors.IsForbidden`
    status-update error) on a branch whose intended `retErr` is nil
    (`InvalidSpec` / `ClassValidation`) → `Reconcile` returns the **non-nil**
    write error, not nil — proving a failed terminal-status write is never
    masked by a nil-error caller branch.
  - Generation capture under conflict: a `finish` write that hits a 409
    where the re-fetched CR's `.metadata.generation` has advanced (a spec
    edit landed mid-retry) → the persisted `ObservedGeneration` is the
    generation the reconcile **acted on** (captured before the retry loop),
    not the newer re-fetched generation.
  - Multiple `ProvisionedPartiEnv` CRs reconcile independently without
    cross-talk.
  - Drift counts: a pre-existing drifting bucket → `LastPlan` drift counts
    by severity match the `PlanResult`.

## Open Design Decisions

1. **CRD API version `v1alpha1`.** A first operator API; not stability-frozen.
   A future `v1` graduation is a follow-up, not Phase 7.
2. **Resync period is a manager flag, not a CR field.** Default 5m. Keeping
   it operator-scoped (not per-CR) keeps the CR purely declarative about
   *desired NATS state*; how often the operator re-checks is an operational
   concern. Revisit if per-environment cadences are genuinely needed.
3. **Single Secret for NATS auth.** One `corev1.Secret` per CR, with optional
   `credentials` / `token` / `nkey` data keys. Mutual TLS / per-key rotation
   is a follow-up.
4. **`force` is honored, not capped.** The controller applies `Spec.Policy`
   verbatim. The continuously-reconciling implication is documented rather
   than designed away — capping the ladder would make the CR a
   second-class config surface vs. the CLI.
5. **No finalizer.** Deleting the CR never deletes NATS resources. If
   opt-in deprovisioning is ever wanted, it is a deliberate future feature
   with its own gating, mirroring Phase 6's two-layer destructive gate.
6. **NATS auth from a Secret** is fully in-memory for all three auth modes:
   `.creds` bytes via `nats.UserCredentialBytes`, token via `nats.Token`,
   and the nkey seed parsed with `nkeys.FromSeed` and signed through a
   `nats.Nkey` callback — no temp file anywhere. An earlier draft used
   `nats.NkeyOptionFromSeed` with a `0600` temp seed file, but that helper
   re-reads the file on *every* nonce signature, including reconnect-time
   signatures after a NATS server restart, so a file deleted post-connect
   would silently break reconnection. The in-memory `nkeys.KeyPair` is held
   for the connection's lifetime and wiped on `close()` (W3).
